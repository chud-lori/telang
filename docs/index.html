Self-hosted object storage, one Go binary

Telegram holds the bytes. Your tools still speak S3.

Telang runs on your own box with your own Telegram credentials. Objects are encrypted locally and stored as messages in a private channel. On the front it answers the AWS S3 wire protocol, so aws s3, rclone, boto3, Cyberduck and the AWS SDKs work against http://localhost:9000 with no Telang-specific client.

Read this part first. Telang suits hobby projects, internal tools, and dev or staging environments. It does not suit production, customer data, or high-throughput public asset serving.

Telegram can ban the account and your data can vanish. That is the deal.

What it implements, and what it refuses

Taken from the request router, not from intent. Anything in the right column answers NotImplemented rather than pretending.

Implemented

  • Signature V4 in four payload modes: hex SHA-256 body hash, UNSIGNED-PAYLOAD, STREAMING-AWS4-HMAC-SHA256-PAYLOAD, and STREAMING-UNSIGNED-PAYLOAD-TRAILER.
  • Presigned URLs, signed entirely in the query string.
  • ListObjectsV2 with prefix, delimiter, pagination and start-after.
  • Multipart upload, and single-range GET.
  • AES-256-GCM encryption of every object before it leaves the box, with a per-bucket key.
  • A disk LRU cache of ciphertext, so a warm read never calls Telegram.
  • A small server-rendered browser UI for listing, download, upload and delete.

Not implemented

  • Versioning, ACLs, bucket policy, CORS, lifecycle, replication, tagging, object lock, website and logging subresources.
  • Server-side encryption variants (SSE-C, SSE-KMS). Encryption is unconditional and client-invisible.
  • CopyObject and multi-object delete (POST /{bucket}?delete). Neither is routed.
  • More than one credential pair. One access key and one secret key per install. Put a reverse proxy in front if you need more.
  • Acting as a CDN. Telegram is not a CDN.

Install

Go 1.25 or newer is required (go.mod declares go 1.25.0). There are no published binaries and no tagged releases yet, so both routes build from a clone.

Build from source

shell
git clone https://github.com/chud-lori/telang
cd telang
go build -o telang ./cmd/telang
./telang --help

Or run it in a container

The image is not published anywhere, so build it locally. The Dockerfile produces a CGO-free static binary on Alpine, exposes port 9000, and expects /etc/telang and /var/lib/telang as volumes.

shell
docker build -t telang:local .
docker run --rm -p 9000:9000 \
  -v "$PWD/etc":/etc/telang \
  -v "$PWD/var":/var/lib/telang \
  telang:local serve --config /etc/telang/config.toml

go install does not work yet. go.mod declares the module path github.com/telang/telang while the repository lives at github.com/chud-lori/telang, so neither spelling resolves: one points at a different module, the other fails Go's module path check. Clone and build until those two agree.

Commands

The complete subcommand list. telang --help prints the same thing. Every command takes --config, which defaults to /etc/telang/config.toml.

Subcommands and their flags
CommandFlagsWhat it does
init --config, --keys, --data-dir, --listen Interactive setup. Writes config.toml and keys.toml at mode 600, prints a generated access key and secret key.
serve --config Runs the daemon. In bot mode it checks the token and the channel before it starts listening, so a revoked token fails at startup. Shuts down on SIGINT or SIGTERM with a 30 second drain.
reauth --config Signs in again when an MTProto session has expired, and rewrites the session file.
fsck --config, --fix Walks every row in the index and asks the backend whether the message still exists. Reports orphans. Changes nothing unless --fix is passed, which deletes the orphaned rows.
export-metadata --config Writes the object index to stdout as JSONL. Keep it with your key backup.
import-metadata --config Reads that JSONL back from stdin. This is the recovery path after a lost index or a new account.

Flag names and defaults come from the flag sets in cmd/telang/. Exit code 1 on failure, 2 on an unknown subcommand.

What a stored object looks like

An object is encrypted before it is uploaded, and the layout is the same on Telegram and in the local cache. Telegram only ever holds the ciphertext.

header
17 bytes
frame 0 ciphertext
64 KiB
tag
16 B
frame 1 ciphertext
64 KiB
tag
16 B
...

version byte, 12 byte base nonce, 4 byte frame size AES-256-GCM frame GCM authentication tag

Each frame gets its own nonce, derived by keeping the random part of the base nonce and mixing in the frame index. The frame index is also the additional authenticated data, so reordering or splicing frames fails authentication instead of decrypting to garbage. Framing is what makes a ranged read cheap: a range touches only the frames it covers.

The key is per bucket and lives in keys.toml. Lose that file and the ciphertext stays ciphertext, which is why the daemon refuses to start when the file is readable by anyone else.

Cold reads and concurrent load are not measured.

Ways this bites you

Each one is a real failure mode, not a disclaimer.

The account gets banned

Telegram tolerates this kind of use at small scale but promises nothing. After a ban every object is unreadable until you export the metadata, move to a fresh account, re-fetch the files and import again.

This is the existential risk, and it is the reason for the warning at the top of this page.

keys.toml goes missing

No keys, no plaintext. There is no recovery path and no support channel that can help. Copy it off the host the moment you create a bucket, and keep a metadata export beside it.

Telegram throttles you

The bot backend retries a 429 after the wait Telegram asks for, and backs off 1s, 2s, 4s up to 15s on transient 5xx. When retries run out, the request answers 503 SlowDown, so your client sees the failure rather than a silent stall.

A streaming upload body cannot be replayed, so an upload that hits a flood wait fails on the first attempt. Retry it from the client.
